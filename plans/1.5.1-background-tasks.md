## 1. Findings (A)

Review of the partially ported module (`df0ec1f`) against the legacy branch `feature/T22952-background-tasks`. Each
finding marked `high` prevented tasks from being executed, or broke the distribution of tasks between workers.

### A-01 - Worker never closes tasks

`high` - not breaking

`WorkerTaskContext.onTaskCompleted`, `onTaskCanceled` and `onTaskFailed` were `TODO()`. Every task threw
`NotImplementedError` after the handler returned. Being an `Error`, it bypassed `catch (exception: Exception)` in
`executeTaskRunnable`, so the task's `CompletableFuture` never completed: with RabbitMQ the launch message was never
acknowledged, with the local queue the worker assignment leaked. The task stayed `Running`.

**Implemented:** `BackgroundTaskWorkerBean` rewritten, ported from the legacy worker:

- Each execution step (start, completed, canceled, failed) runs in its own write-locked transaction, publishing the
  domain events recorded by the handler and the entity (new event `BackgroundTaskCompleted`).
- Status messages (`Started`, `Completed` with the handler's result value as JSON, `Failed`, `Canceled`) are broadcast
  *after* the commit, and on a best-effort basis: a failing broadcast is logged, it doesn't fail the task.
- `onFailure` is invoked for failed tasks (its events are published, a requested retry is logged as not supported,
  see Q-03), `onCancel` for canceled tasks. Exceptions in these callbacks are logged, the task is closed regardless.
- Closing is tolerant to concurrent status changes: a task canceled while its handler completes stays canceled, and
  `Canceled` is broadcast instead of `Completed`.

**Decision:** fixed

### A-02 - Tasks never reach `Launched`, so they can't start

`high` - not breaking

`BackgroundTask.create` sets `Created`, `started()` requires `Launched`, but nothing set `Launched`. Every start failed
with `InvalidBackgroundTaskStatus`.

**Implemented:** `BackgroundTask.launched()` sets `Created` → `Launched`, applied by the service after enqueueing (in a
new transaction after the commit, see `publishBackgroundTask`). `started()` accepts `Created` and `Launched`, because
the
worker may pick up the task before the service marked it as launched; `launched()` is a no-op then. A task stuck in
`Created` thus indicates it has never been enqueued (see I-01).

**Decision:** fixed

### A-03 - Worker beans without lifecycle

`high` - not breaking

The workers were created in a `BeanFactoryPostProcessor` and registered with `registerSingleton`, which skips the bean
lifecycle: `afterPropertiesSet` was never called, so `executor` was uninitialized and `acceptsCategory` threw on
registration in the queue; `close` was never called, so the non-daemon executor threads kept the JVM alive after the
context was closed. Additionally, the post-processor resolved the JPA repository, `TransactionService`, `EventBus` etc.
while post-processing the bean factory, instantiating them before the `BeanPostProcessor`s were registered.

**Implemented:** `BackgroundTaskWorkerRegistrar`, a static `BeanDefinitionRegistryPostProcessor` binding the worker
instance properties from the `Environment`, registers a bean definition per worker (`backgroundTaskWorker-<index>`,
previously `backgroundTaskWorkerBean-<index>`) with an instance supplier. Dependencies are resolved when the worker is
instantiated, and the worker is initialized and closed (inferred `AutoCloseable`) like any other bean.

**Decision:** fixed

### A-04 - RabbitMQ: failed task-launch messages stay unacknowledged

`high` - not breaking

If a task-launch message couldn't be deserialized (e.g. request class not on the worker's classpath) or
`worker.submit` threw, the exception propagated from the listener. With `AcknowledgeMode.MANUAL`, the container
neither acknowledges nor rejects the message: it stayed unacknowledged, occupying a prefetch slot (with the fix of A-06,
the worker's only slot, blocking it forever), and was redelivered when the consumer stopped. The task-control binding
was leaked.

**Implemented:** Unreadable messages are rejected without requeue; failed submissions are rejected via the failed
future, removing the binding and the worker assignment. The ack itself is guarded, as the channel may be closed when a
long-running task finishes. Tests: `failedSubmissionIsRejectedWithoutRequeue`,
`unreadableMessageIsRejectedWithoutRequeue`.

**Decision:** fixed

### A-05 - RabbitMQ: task-control messages never acknowledged

`high` - not breaking

The worker-control listener was set to `AcknowledgeMode.MANUAL`, but its plain `MessageListener` can't acknowledge.
After 250 cancellations (the default prefetch count) the consumer received no more control messages, and cancellation
stopped working until restart.

**Implemented:** `AcknowledgeMode.AUTO` without re-queueing rejected messages, unreadable messages and failing
operations are logged. Test: `controlMessagesAreAcknowledged` (260 cancellations).

**Decision:** fixed

### A-06 - RabbitMQ: workers prefetch up to 250 tasks

`high` - not breaking

Launch messages are acknowledged when the task has finished, and the listener containers used the default prefetch
count of 250. A single-threaded worker therefore received up to 250 pending tasks, queueing them in its executor, while
idle workers on other instances got nothing.

**Implemented:** `BackgroundTaskWorker.maxConcurrentTasks` (new interface property, default `1`), the prefetch count of
the worker's listener container. `BackgroundTaskWorkerBean` derives it from its configuration: `1` for `SingleThread`,
`thread-pool-size` otherwise (so `thread-pool-size` now also limits the concurrency of `CachedThreadPool` and
`VirtualThreads` workers with RabbitMQ). Test: `workerReceivesOnlyAsManyTasksAsItExecutesConcurrently`. See also I-07.

**Decision:** fixed

### A-07 - Canceling queued tasks fails, row locked while signaling

`high` - not breaking

`cancel` marked the task as canceled and then signaled the worker *within* the transaction, holding the task's write
lock while waiting for the worker's reply. Canceling a task that wasn't running yet failed and rolled back the
cancellation: the local queue threw `UnknownTaskHandle` (no worker assigned yet), RabbitMQ waited for the reply timeout
(10 s, nobody bound to the routing key) and threw `TaskControlFailed`.

**Implemented:** The worker is signaled after the commit, and only if the task was `Running` (a running task is always
bound to its worker). A task that is not running yet is skipped by the worker picking it up, which invokes `onCancel`
and broadcasts `Canceled`. If the signal fails, `cancel` logs it and returns `false` (the task stays canceled), as
documented in `BackgroundTaskService.cancel`. The local queue returns `false` for unassigned tasks instead of throwing.
Test: `cancelQueuedTask`.

**Decision:** fixed

### A-08 - Worker execution edge cases

`medium` - not breaking

- The executor future was registered in `runningTasks` *after* submitting it: a fast task removed the entry before it
  was added, leaking it.
- Canceling a task still waiting in the executor (`future.cancel`) prevented the runnable from ever running, so the
  task's `CompletableFuture` never completed.
- Cancellation was only detected via `InterruptedException` in the cause chain; interrupted I/O
  (`InterruptedIOException`, `ClosedByInterruptException`, e.g. JDBC) was treated as a failure.
- The task ID lookup and handler resolution ran in the caller's thread (for the local queue in the service's
  `afterCommit`), and a missing handler threw an `AssertionError`, escaping the compensation in `afterCommit`.

**Implemented:** A `TaskExecution` runnable is registered before execution, and cancellation interrupts its thread only
while it runs (cancellation is also tracked in a flag, so a handler swallowing the interrupt is still treated as
canceled). Lookup and resolution run in the worker thread; a missing handler (`MissingBackgroundTaskHandler`, a
`DomainException`) fails the task. Redelivered tasks that are not startable anymore (`Running`, closed) are skipped with
a warning (see I-01). Errors other than `VirtualMachineError` thrown by a handler also fail the task.

**Decision:** fixed

### A-09 - Changelog does not match the entity mapping

`high` - not breaking

`spring.jpa.hibernate.ddl-auto=validate` failed with the changelog on MariaDB and PostgreSQL: `handle` was declared as
Liquibase `uuid` (native `uuid` type), but is mapped as `varchar(36)`. Timestamps used `timestamp` instead of the
`datetime` of the other Kiwi changelogs (MySQL `TIMESTAMP` has a 2038 limit and time zone conversion).

**Implemented:** `handle` is `varchar(36)`, timestamps are `datetime`, `request_data` is `jsonb` on PostgreSQL (as
mapped by Hibernate) and `json` otherwise. The changelog is unreleased, so the change set was amended in place. Test:
`BackgroundTaskSchemaValidationTest` (MySQL 8, MariaDB 11, PostgreSQL 17); the previous changelog fails it on MariaDB
and PostgreSQL.

**Decision:** fixed

### A-10 - `BackgroundTaskService` requires a `ConversionService` bean

`low` - not breaking

The service bean required a `ConversionService` bean, which only Web MVC applications declare (`mvcConversionService`).

**Implemented:** Falls back to `ApplicationConversionService.getSharedInstance()`. The Kiwi framework itself still
requires the bean, see Q-06.

**Decision:** fixed

### A-11 - Messaging provider required without workers

`low` - not breaking

`kiwi.background-task.messaging.provider` was required on every instance, although only workers broadcast messages, so
server-only instances (`worker.enabled=false`) had to configure messaging.

**Implemented:** The messaging bean moved into the worker configuration, the provider is only required with workers.

**Decision:** fixed

### A-12 - Minor fixes

`low` - not breaking

- `BackgroundTaskStatus.isRunning` defaulted to `true`, so every status was "running". Now only `Running`.
- `lookup` took a pessimistic read lock, blocking on tasks write-locked by a status change. Now a plain read.
- RabbitMQ messages are sent with content type `application/json`.
- Properties: `queue.rabbit-mq` and `messaging.simp` are `val` groups like the other groups, `categories` is `var`.
  The properties are documented in KDoc (configuration metadata), `ConfigurationMetadataTest` checks them.
- KDoc amended for the module's public types, `AbstractProviderCondition`, and `BackgroundTaskService`.

**Decision:** fixed

### A-13 - Tests

`high` - not breaking

The module had no tests. Ported from the legacy branch (adapted to the current API):

- `BackgroundTaskQueueHarness` with `TestBackgroundTaskWorker`/`TestBackgroundTaskMessaging`, run by

## 2. Open questions (Q)

### Q-01 - Launch in an independent transaction

`medium` - not breaking

`launch` persists the task with `writeNew`, suspending the caller's transaction: the task is committed and enqueued even
if the caller's transaction rolls back afterward (e.g. a command handler failing after launching a task). Joining the
caller's transaction (`write`) would enqueue the task only if the caller commits, and fail the caller's commit if the
queue is unavailable.

**Proposal:** join the caller's transaction, which is the expected semantics of a side effect in a command. Keep
`writeNew` only if tasks are meant to be launched regardless of the caller's outcome.

**Decision:** Accept proposal, join task launch with caller transaction

**Implemented:** `launch` uses `TransactionService.write`, joining the caller's transaction (or starting one), and
publishes the `BackgroundTaskCreated` event in it. The task is enqueued after the caller's commit; if the queue is
unavailable (`beforeCommit`), the caller's commit fails. `cancel` keeps its own transaction (`writeNew`), as the
worker is signaled after the commit and must not wait for the caller's lock. Test: `launchJoinsCallerTransaction`.

### Q-02 - `Canceled` message for tasks not started yet

`low` - not breaking

The `TODO` in `BackgroundTaskServiceBean.cancel`: the `Canceled` message of a task that wasn't running is only broadcast
when a worker picks it up (A-07), which may take long if the workers are busy. The service has no
`BackgroundTaskMessaging` dependency, as messaging is only required with workers (A-11). The legacy service broadcast it
immediately.

**Proposal:** keep it as is, the caller of `cancel` knows the outcome from the return value.

**Decision:** Accept proposal, only send message from worker

**Implemented:** `TODO` replaced by a comment, `BackgroundTaskService.cancel` KDoc documents that the worker picking up
the task broadcasts `Canceled`. Status `rejected` refers to the change (an immediate message), not the proposal.

### Q-03 - Handler callbacks and retries

`medium` - not breaking

- `onFailure` and `onCancel` are abstract, so every handler implements three methods. The legacy `onCancel` had a
  default implementation.
- The `FailureResponse` of `onFailure` suggests retries, which are not implemented: a retry needs a new delivery
  (RabbitMQ: delayed requeue or a retry queue with TTL), and the status model a transition back from `Running`.
- `onCancel` is also invoked for tasks canceled before they started (documented), unlike the legacy worker.

**Proposal:** default implementations (`noRetry()`, `DomainResult.empty`); remove `FailureResponse` until retries are
designed, or keep it documented as not supported.

**Decision:**

- No default implementation, decision should be explicit on client-side without the possibility of being forgotten about
- Keep `FailureResponse` documented as not supported, will be prioritized in an upcoming draft

**Implemented:** Nothing to change: the callbacks stay abstract, `onFailure` KDoc states that retries are not supported
yet, and the worker logs a requested retry. Retries remain open for the upcoming draft.
Retries have been implemented with F-09 (2026-11-13).

### Q-04 - Authorization of task cancellation

`medium` - not breaking

`cancel(taskHandle, user)` doesn't check the user: anybody knowing the handle can cancel the task. The handle is secret
and random, but it is also sent to clients and appears in logs.

**Proposal:** allow cancellation by the creating user and admins only, or let the application decide (the service is
called by application code, which may check access before).

**Decision:** Defer for later, will be prioritized in separate proposal with authorization/access-provider interface for
background tasks provided by client applications

### Q-05 - Error details sent to clients

`medium` - not breaking

The `Failed` message contains the exception class name and message, which may disclose internals (SQL, paths) to the
client subscribed to the task. The entity stores them as well (fine, internal).

**Proposal:** send the code and arguments of `DomainException`s, and a generic error otherwise.

**Decision:** Accept proposal, match response contents with DomainException response rendering

**Implemented:** New API type `BackgroundTaskError(message, arguments, errorType)`, matching `ErrorBody` of the web
layer's `ExceptionResponseManager`: code, arguments and class name of a `DomainException`; for other exceptions the
generic `unknown-exception` with type `DomainException.Unknown` and no arguments (unlike the web layer's fallback, which
includes the exception message and type). `StatusChanged.Failed` carries an `error: BackgroundTaskError` instead of
`errorClassName`/`errorMessage` (**API change**). The entity stores the error as JSON (`error_data`) for
`lookupDetails` (I-02), and still records the exception class and message internally. The background-tasks module
doesn't depend on the web layer, so the rendering is reimplemented, not reused. Tests: `failingTasks`,
`taskWithoutHandlerFails`, `failedTaskRecordsDomainError`.

### Q-06 - Kiwi framework requires a `ConversionService` bean

`low` - not breaking

Not part of this module: `AnalyticalReportConfiguration` of the Kiwi framework requires a `ConversionService` bean, so a
non-web application (e.g. a dedicated worker instance with `spring.main.web-application-type=none`) fails to start. The
integration tests declare an `ApplicationConversionService` bean.

**Proposal:** fall back to `ApplicationConversionService.getSharedInstance()` like A-10, in the framework.

**Decision:** Update AnalyticalReportConfiguration to fallback on ApplicationConversionService bean

**Implemented:** `AnalyticalReportConfiguration` resolves the `ConversionService` via `ObjectProvider.getIfUnique`,
falling back to `ApplicationConversionService.getSharedInstance()` (`bundle` module). The integration test application
doesn't declare a `ConversionService` bean anymore. Remark: `docs/07-testing.md` lists the `ConversionService` among
the beans a slice test must declare, which is now only needed for the web endpoints.

## 3. Further change ideas (I)

### I-01 - Recovery of orphaned tasks

`high` - not breaking

Tasks can be orphaned without a way to recover them:

- `Created`: the service instance died between the commit and enqueueing (the dual write is only alleviated by
  `checkAvailable`).
- `Running`: the worker died. RabbitMQ redelivers the launch message, but the next worker skips it, as the task is not
  startable anymore (A-08), so the task stays `Running`. The local queue loses it entirely.

**Proposal:** a periodic sweeper (enqueue `Created` tasks older than a threshold, fail or restart `Running` tasks of
dead workers), with a worker heartbeat or the worker handle recorded on the task.

### I-04 - RabbitMQ dead-lettering and queue length limit

`medium` - not breaking

- `dead-letter-exchange` and `dead-letter-task-launch-queue` are not used (documented as such): rejected launch
  messages are dropped. The task status records the failure anyway, except for unreadable messages (A-04).
- `max-queue-length` (`x-max-length`) uses RabbitMQ's default overflow `drop-head`, silently dropping the *oldest*
  pending tasks, which then stay `Launched` forever.

**Proposal:** wire the dead-letter exchange, and use `x-overflow: reject-publish` with publisher confirms, so enqueueing
fails (and the task is marked failed) instead.

**Decision:** Accept proposal: Wire up dead-letter exchange, switch to reject-publish behavior.

**Implemented:**

- Durable dead-letter exchange and queue are declared, every task-launch queue dead-letters to them
  (`x-dead-letter-exchange`, `x-dead-letter-routing-key`). Rejected launch messages (unreadable, failed submission or
  execution) are retained in the dead-letter queue, which isn't consumed.
- With `max-queue-length`, queues use `x-overflow: reject-publish`.
- Enqueueing waits for the publisher confirm (new property `publish-confirm-timeout`, 10 seconds) if the connection
  factory has confirms enabled (`spring.rabbitmq.publisher-confirm-type=correlated`), and fails on a nack, timeout, or
  (with `spring.rabbitmq.publisher-returns=true`) an unroutable message; the task is then marked failed by the
  compensation.
  Without confirms, a warning is logged at startup: rejected launch messages are lost, the tasks stay `Launched`.
- With publisher returns, the template is `mandatory`, so a cancel signal for a task without bound worker fails
  immediately (`no-worker-bound`) instead of after `wait-for-reply-timeout`.
- Remark: Changing queue arguments of existing queues fails their declaration (`PRECONDITION_FAILED`), so queues
  declared by earlier development versions must be deleted. Unreleased, so not breaking.
- Tests: `failedSubmissionIsRejectedWithoutRequeue`, `unreadableMessageIsRejectedWithoutRequeue` (dead-lettered),
  `fullQueueRejectsLaunch`, `cancelUnassignedTaskFails`.

### I-05 - Graceful worker start and shutdown

`medium` - not breaking

- Workers are registered in the queue in `SmartInitializingSingleton`, so RabbitMQ consumers start receiving tasks
  before the application has fully started.
- `close` shuts down the executor without waiting: running tasks continue while the context (and the database
  connections) shut down, and the RabbitMQ queue may be destroyed before them, so their acknowledgement fails and the
  task is redelivered (see I-01).

**Proposal:** register workers as `SmartLifecycle`, stopping consumers first, then awaiting running tasks with a
configurable timeout before interrupting them.

**Decision:** Accept proposal, improve worker registration

**Implemented:**

- `BackgroundTaskWorkerLifecycle` (`SmartLifecycle`, phase below Spring Boot's web server lifecycles) replaces the
  `SmartInitializingSingleton` registrar: workers are registered in the queue on start, so they receive tasks once the
  context has been refreshed.
- On stop, workers are unregistered first (new `BackgroundTaskQueue.unregisterWorker`), then shut down concurrently (new
  `BackgroundTaskWorker.shutdown(timeout)`): running tasks may finish within `worker.shutdown-timeout` (new
  property, 30 seconds). Tasks still running afterward are aborted: interrupted, `onFailure` is invoked with
  `BackgroundTaskWorkerShutdown`, and they are marked failed. Tasks not started yet are dropped (they stay `Launched`).
- RabbitMQ: Unregistering stops the worker's consumers, which closes their channels, so the broker re-queues the launch
  messages of the worker's running tasks. They are redelivered to other workers, which skip them (not startable
  anymore), and the original acknowledgement fails with a logged warning. Keeping the channels open until the tasks
  finish isn't possible with the `DirectMessageListenerContainer` without new deliveries. The task-control bindings
  are kept, so running tasks can still be canceled during the shutdown.
- Tests: `BackgroundTaskWorkerShutdownIntegrationTest` (local queue), `unregisterWorker` (both queues).
  The RabbitMQ shutdown path is only covered by the queue-level test.

### I-08 - Debounce task state updates from the context

`medium` - not breaking

Recorded with the decision on I-03. Every `emitProgress` loads, write-locks and stores the task in its own transaction,
which doesn't scale to handlers reporting progress frequently (e.g. per processed item), and contends with the lock
taken by `cancel`.

**Proposal:** Debounce updates of the task entity per task execution; broadcast messages immediately (or throttled),
but store the latest progress at most every `n` milliseconds (configurable), plus once when the task is closed (within
the closing transaction, which loads and locks the task anyway). The cancellation point currently provided by
the update would be replaced by an explicit check of the interrupt flag.

**Decision:** Throttle broadcasting of messages to at most once per duration, plus once when the task is closed. Store
the progress along with broadcasting, keeping a local progress value and updating it throttled when changed. Use a timer
or (virtual) thread within the context; design according to best practices.

**Design:** One `TaskMessageThrottle` per task execution (created by `WorkerTaskContext`), with a virtual thread
started lazily on the first message (tasks without messages need no thread), terminated when the task is closed.
Alternatives considered: A shared `ScheduledExecutorService` per worker needs a second executor for the blocking work
(transaction, broadcast), plus coordination so flushes of a task don't overlap and closing waits for them; a per-task
virtual thread gets both for free, and costs next to nothing while waiting. The handler thread never blocks on I/O when
emitting, only on a short lock (`ReentrantLock`, no pinning of virtual threads).

- Leading edge: The first message after an idle interval is flushed immediately, then the thread waits for the
  interval (woken early only by closing).
- Pending messages are kept in emission order. `Progress` is conflated: a new progress replaces the pending one (at the
  new position), and is skipped if it equals the last flushed progress.
- A flush stores the latest progress (if any, and the task is still running) in one transaction, then broadcasts the
  batch; the progress message is only broadcast if the stored progress changed.
- Closing the task closes the throttle first: the thread is stopped (waiting up to 10s for a flush in progress), and the
  remaining messages are returned. Their progress is stored in the closing transaction (no extra transaction), and they
  are broadcast after the commit, before the status message. Messages emitted afterward are discarded.
- Memory bound: At most `max-pending-messages` messages other than progress are retained between flushes, older ones
  are dropped with a warning.
- `emitMessage` is a cancellation point via an explicit check of the interrupt flag (instead of the transaction).

**Implemented:** `TaskMessageThrottle` (application package), used by `BackgroundTaskWorkerBean.WorkerTaskContext`.
New properties `kiwi.background-task.worker.message-throttle-interval` (default `1s`, `0` disables throttling) and
`kiwi.background-task.worker.max-pending-messages` (default `1000`). KDoc of `BackgroundTaskContext.emitMessage`
updated. Tests: `TaskMessageThrottleTest` (unit, 8 tests); integration tests assert the throttled progress (subsequence
of the emitted progress, latest always broadcast) and coalescing (`progressIsThrottled`, 100 progress
updates within one interval yield at most 2 progress messages).

Remarks:

- If closing the throttle is interrupted (e.g. `shutdownNow` while closing), the interrupt is restored, and the closing
  transaction fails like before (existing behavior of `transactionWithTask`).
- Messages are delayed by up to one interval; clients relying on every progress value only see the latest.

## 4. Redesign and features (R, F)

Requested on 2026-11-09 after committing the first draft (`acc904b`): The single `emitMessage` funnel leaks the message
types into the API and complicates the worker. Large and breaking changes are in scope. Proposed order of work:

1. **Phase 1 - Refactoring** (R-01, R-02): new context API and internal units, behavior unchanged otherwise.
2. **Phase 2 - Features** (F-01, F-02, F-03): status, scratchpad, stages, built on the units of phase 1.
3. **Phase 3 - Resume** (F-04): executing an interrupted task again, using the scratchpad and stage checkpoints.

Database changes amend the unreleased `db.background-tasks-1.5.1.yaml` in place.

### R-01 - Dedicated context methods, messaging internal

`high` - breaking (API)

**Proposal:** `BackgroundTaskContext` offers dedicated methods with simple arguments, the message types and the
messaging infrastructure move into the module (`de.kiwi.backgroundTask.messaging`):

```kotlin
interface BackgroundTaskContext {
    val taskHandle: UUID
    val request: BackgroundTaskRequest
    val user: BackgroundTaskUserDescriptor
    val attempt: Int                          // 1, or higher if resumed (F-04)

    val status: BackgroundTaskExecutionStatus // F-01
    fun checkActive()                         // cancellation point, throws InterruptedException

    fun reportProgress(percent: Int)          // plain progress, for handlers without stages (F-03)
    fun sendNotification(message: String, arguments: Map<String, Any?> = emptyMap())
    fun sendMessage(messageType: String, details: Any?)

    val scratchpad: BackgroundTaskScratchpad  // F-02
}
```

- Removed from `api`: `BackgroundTaskMessage` (moves to the module, still the wire format of the SIMP topic),
  `emitMessage` and its extensions, `BackgroundTaskContext.descriptor` (replaced by `taskHandle` and `request`).
- Added to `api`: `BackgroundTaskProgress` (percent and the current stage: name, index, count, completed and total
  items), returned in `BackgroundTaskDetails.progress` and sent in the `Progress` message.
- `BackgroundTaskError`, `BackgroundTaskDetails`, `BackgroundTaskStatus` stay in `api` (returned by the service).

**Decision:** accepted. Notifications and custom messages are sent immediately; progress calculation and progress
messages are throttled.

**Implemented:** As proposed, with these differences:

- Message types and `BackgroundTaskMessaging` moved to `de.kiwi.backgroundTask.application.messaging`. `UserMessage` is
  gone: `Progress` (with a `BackgroundTaskProgress`), `Notification` and `Custom` are direct subtypes. `Started` carries
  the `attempt`.
- `reportProgress(percent)` is a default method delegating to `reportProgress(BackgroundTaskProgress)`, which the stages
  DSL uses. Reporting progress is no cancellation point anymore; `checkActive()` is the explicit cancellation point.
- `BackgroundTaskDetails.progressPercent` became `progress: BackgroundTaskProgress`, plus `attempt`.
- `BackgroundTaskExecutionStatus` values: `Running`, `CancelRequested`, `AbortRequested` (worker shutdown, or superseded
  by a resumed attempt).

### R-02 - Split the worker into dedicated units

`high` - not breaking

`BackgroundTaskWorkerBean` (540 lines) combines the executor, the execution lifecycle, the context, the transactions of
all status changes, throttling and broadcasting.

**Proposal:** One responsibility per unit, each unit-testable on its own:

| Unit                       | Responsibility                                                                                                                                                        |
|----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `BackgroundTaskWorkerBean` | Executor, `submit`/`cancel`/`shutdown`, registry of running executions                                                                                                |
| `TaskExecution`            | Lifecycle of one execution: resolve handler, start, handle, close; cancel/abort flags and the executing thread                                                        |
| `TaskExecutionContext`     | Implements `BackgroundTaskContext`, delegates to the units below                                                                                                      |
| `TaskProgressTracker`      | Pure, thread-safe state: stage plan, current stage, items, plain progress; computes `BackgroundTaskProgress` snapshots                                                |
| `TaskOutbox`               | Pending notifications/custom messages (bounded, in order)                                                                                                             |
| `TaskSupervisor`           | Per-execution virtual thread (replaces `TaskMessageThrottle`): ticks at most once per interval, syncs progress and status, broadcasts the outbox; final sync on close |
| `BackgroundTaskStateStore` | Transactions of the task entity (start, complete, fail, cancel, sync progress, scratchpad), event publishing; replaces the `transactionWithTask` lambdas              |

The supervisor syncs *state* instead of conflating messages: Each tick takes a progress-snapshot (persisted and
broadcast if changed) and drains the outbox. The tick's transaction also reads the task status (F-01), and later renews
the lease (F-04).

**Decision:** accepted (with R-01: notifications bypass the supervisor, only progress is throttled).

**Implemented:** Units in `application` and `application.worker` (internal):
`BackgroundTaskWorkerBean` (executor, ~140 lines), `TaskExecution` (lifecycle, implements `TaskExecutionControl`),
`TaskExecutionContext`, `TaskSupervisor` (replaces `TaskMessageThrottle`), `TaskScratchpad`, and
`BackgroundTaskStateStore` (bean, all transactions of executions, with ownership checks). There is no `TaskOutbox`, as
notifications are sent immediately. `TaskProgressTracker` moved into the stages DSL (API module): the DSL computes
`BackgroundTaskProgress` snapshots, the supervisor only throttles and syncs them. Properties
`worker.message-throttle-interval` and `worker.max-pending-messages` were replaced by `worker.progress-interval`
(default `1s`) and `worker.lease-duration` (default `1m`, renewed every third).

### F-01 - Task status in the context

`medium` - not breaking

**Proposal:** `context.status` returns the execution status as seen by the worker, without a database query:

```kotlin
enum class BackgroundTaskExecutionStatus { Running, CancelRequested, ShutdownRequested }
```

- Updated immediately by the worker's cancel signal and shutdown, and by each supervisor tick from the database: A
  task canceled in the database is detected even if the cancel signal got lost, and the handler is interrupted.
- `checkActive()` throws an `InterruptedException` unless `Running`; it is also called by the stage helpers between
  work items (F-03).
- Handlers can react, e.g. finish the current item and store a checkpoint before propagating the interruption.

**Decision:** accepted.

**Implemented:** As proposed (`AbortRequested` instead of `ShutdownRequested`). The supervisor's sync (progress or lease
renewal, at least every third of the lease duration) detects a cancellation in the database and a superseded attempt,
and requests the execution to stop.

### F-02 - Task scratchpad

`high` - not breaking

**Proposal:** A key-value store per task, for checkpoints and intermediate results that survive a failed or interrupted
execution:

```kotlin
interface BackgroundTaskScratchpad {
    operator fun contains(key: String): Boolean
    fun <T : Any> get(key: String, type: Class<T>): T?   // + reified extension get<T>(key)
    fun put(key: String, value: Any)                      // durable when it returns
    fun remove(key: String)
    val keys: Set<String>
}
```

- Table `kiwi_background_task_data` (`task_id`, `data_key`, `data_value` as JSON, `updated_on`), primary key (`task_id`,
  `data_key`). One row per key, so writing a key doesn't rewrite the other entries (e.g. one key per sent
  e-mail).
- Loaded once when the execution starts, cached; writes are write-through in their own transaction, without locking the
  task row (no contention with `cancel`). Not throttled: a checkpoint must be durable before the next side effect.
- Guarantee: at-least-once for side effects. A crash between a side effect and its `put` repeats that one side effect;
  documented, as exactly-once isn't possible with external systems.
- Retention: see decision.

**Decision:** accepted. Retention: keep the scratchpad of failed tasks (for resuming), delete it when a task is canceled
or completed successfully.

**Implemented:** `BackgroundTaskScratchpad` is an abstract class (so the reified `get<T>(key)` needs no import); keys
starting with `kiwi:` are reserved. Entity `BackgroundTaskData` (table `kiwi_background_task_data`, FK with cascade
delete, unique `(task_id, data_key)`), `BackgroundTaskDataRepository`. Values are loaded lazily on first access and
written through (`BackgroundTaskStateStore.putScratchpadValue`), only while the execution owns the task: a superseded
execution gets a `TaskNotOwned` exception and is aborted. The write-transaction takes a read lock on the task: Without
it, MariaDB's snapshot isolation fails the insert ("Record has changed since last read"), as the supervisor updates the
task row concurrently.

### F-03 - Progress stages and work items

`high` - not breaking

**Proposal:** The DSL as sketched, with the stage helpers using the scratchpad for resumable work items:

```kotlin
override fun handle(request: CopyFilesRequest, context: BackgroundTaskContext) = BackgroundTaskResult(context) {
    val files = stage("gather", quota = 1) {
        gatherFiles(request.fromPath)
    }
    val copied = stage("copy", quota = 8) { stage ->
        // Declares the total items, skips items completed by a previous attempt, marks each item completed
        stage.forEachItem(files.value, key = { it.name }) { file ->
            copyFile(file, request.toPath)
        }
    }
    stage("verify", quota = 1) {
        verifyFiles(files.value, copied.value)
    }
    // last stage result is the task result
}
```

- `BackgroundTaskResult(context) { ... }` returns `DomainResult<T>`. The block is invoked twice:
    1. Planning: `stage` records name and quota and returns a placeholder; accessing its `value` throws a dedicated
       exception explaining that results are only available within later stages.
    2. Execution: `stage` runs the stage lambda, results are available to later stages.
- The block's result is the task result; a returned `StageResult<T>` is unwrapped to `T`.
- Validation: unique stage names, positive quotas, the executed stages must match the plan (same names, same order).
- `StageScope` (stage lambda argument): `totalItems(n)`, `itemCompleted(count = 1)`, `forEachItem(items, key) { }`,
  `reportFraction(f)` for stages without discrete items (indeterminate otherwise), `record(event)` for domain events
  (merged into the task's `DomainResult`).
- Progress: `(sum of completed quotas + quota × stage fraction) / sum of quotas`, the stage fraction from items or
  `reportFraction`, `0` while indeterminate. The current stage is included in `BackgroundTaskProgress`.
- Rules for the block, documented: only `stage` calls (and deterministic declarations) outside the stage lambdas, as
  that code runs twice; stages must not be declared conditionally on stage results.
- Resume (F-04): completed stage results are stored in the scratchpad and restored instead of running the stage
  again; `forEachItem` stores completed item keys.

**Decision:** accepted. Persist the results of completed stages, and skip those stages on resume, reusing the
serialized results.

**Implemented:** In the API module (`BackgroundTaskResult.kt`): `BackgroundTaskResult` (object with `invoke`),
`BackgroundTaskStages` (abstract class with the reified `stage(name, quota) { }`), `BackgroundTaskStage`, `StageResult`,
`StageResultUnavailable`, and the internal `StagedTaskRunner` (two passes, progress calculation). `forEachItem` adds to
the stage's total items (so a stage may call it several times). Unit and `null` results are restored without
serialization. Tests: `BackgroundTaskResultTest` (API, 11 tests), integration tests with a resumable mailing handler.

Remarks:

- Code at the top level of the block runs twice (planning and execution), e.g. the test handler had to record its
  invocation outside the block. Documented on `BackgroundTaskResult`; a common pitfall.
- Stage results are restored with the reified type of `stage<T>`; generic types (e.g. `List<Path>`) work, but the type
  must be deserializable by the application's `ObjectMapper`.

**Current state** (rewritten by the user in `68f88ef`, supersedes the *Implemented* notes above): Stages are run by
`context.stages { }` (`BackgroundTaskContext.stages`, returning `DomainResult<T>`); `BackgroundTaskResult` is gone.
The API (`BackgroundTaskStages.kt`) declares `BackgroundTaskStages` (`stage(name, skippable, quota) { stage -> }`,
`Declaration<T>` must return a `BackgroundTaskStageResult`), `BackgroundTaskStage` (`totalItems`, `itemsCompleted`,
`fractionCompleted`, `forEachItem`, `mapEachItem`, `record`), `BackgroundTaskStageBlock` and
`BackgroundTaskStageResult`. Only `skippable` stages store their result and are skipped on resume; item checkpoints
are stored regardless. Scratchpad keys are reserved with the prefix `kiwi:` (`kiwi:stage:<name>:result`,
`kiwi:stage:<name>:item:<key>`). The runner is internal to the module (`TaskExecutionStages`, tests
`TaskExecutionStagesTest`). Stage events are published per completed stage, and resumed progress doesn't drop (see
the progress log of 2026-11-10).

### F-04 - Resume interrupted tasks

`high` - not breaking

The scratchpad and stage checkpoints only pay off if an interrupted task is executed again. Today, a task running on a
worker that crashes stays `Running` forever (I-01): RabbitMQ redelivers the unacknowledged launch message, but the
receiving worker skips it as `Running`. A task aborted by a worker shutdown is marked `Failed`.

**Proposal:** Lease-based ownership of running tasks:

- New columns `worker_handle`, `lease_expires_on`, `attempt`. Starting a task takes the lease, the supervisor renews it
  (e.g. every 10s, lease 60s).
- A worker receiving a `Running` task with an expired lease takes it over as a new attempt (`attempt + 1`, `onResume`
  semantics via `context.attempt`); with a valid lease, the message is requeued (not acknowledged) instead of dropped.
- Worker shutdown: tasks still running after the shutdown timeout release their lease and return to `Launched`
  (requeued) instead of `Failed`, unless the handler opts out.
- Local queue: Launched/expired tasks are recovered on startup (overlaps with I-01).
- Retries after failures (`FailureResponse.retry`, Q-03) stay deferred, but would use the same mechanism.

**Decision:** Implement leases and resume now, but monitoring and resuming are *manual*, via Spring Boot Actuator
management endpoints (HTTP requests to check on tasks and to resume them). No automatic takeover of expired leases.

**Implemented:**

- Columns `attempt`, `worker_name` (`<pid>@<host>/<beanName>`, not secret, unlike the worker handle),
  `lease_expires_on`,
  and `user_data` (the launching `BackgroundTaskUserDescriptor`, so a resumed task runs on behalf of the same user).
  Entity methods `started(workerName, leaseDuration, clock)`, `renewLease`, `isLeaseExpired`, `isResumable`,
  `resumed(resumedBy, clock)` (Failed, or Running with expired lease -> Created; event `BackgroundTaskResumed`).
- `BackgroundTaskServiceBean.resume(taskId, resumedBy)` enqueues the task again (same dual write as `launch`).
- `BackgroundTaskManagement` (list, details with scratchpad keys, resume) and the `@WebEndpoint` `backgroundTasks`
  (`KiwiBackgroundTaskManagementAutoConfiguration`, Actuator is a `compileOnly` dependency):
  `GET /actuator/backgroundTasks[?status=..&expiredLeases=true&limit=..]`, `GET /actuator/backgroundTasks/{id}`,
  `POST /actuator/backgroundTasks/{id}/resume`. Tasks are identified by their ID (the handle stays secret); errors are
  `400`/`404`/`409` with `{error, message}`.
- Worker shutdown still fails running tasks (`BackgroundTaskWorkerShutdown`), which keeps their scratchpad, so they can
  be resumed.
- Tests: domain tests (lease, resume), integration tests for resuming a failed task without repeating side effects,
  resuming an orphaned task (expired lease), a superseded attempt (state store), and invalid management requests.

Remarks:

- The endpoint must be exposed (`management.endpoints.web.exposure.include=backgroundTasks`) and secured by the
  application. It's tested by invoking the endpoint bean; the HTTP mapping isn't covered by a test.
- A superseded execution (lease expired while it was still running, then resumed) notices within a lease renewal
  interval, or on its next scratchpad write; until then, both attempts run. The lease duration should be well above
  the expected pauses (GC, database outages).
- RabbitMQ still acknowledges a redelivered launch message of a `Running` task (skipped); recovering it is the manual
  resume. Retries after failures (`FailureResponse.retry`) are still unsupported; the warning points to resuming.

## 5. Branch review findings (A-15 to A-25)

Found on review of the branch against `main` (`68f88ef`, 2026-11-10). Verified against the code; implemented as decided.

### A-15 - Superseded close between resume and restart

`high` - not breaking

`BackgroundTaskLifecycleManager.closeIfOwned` and `cancelTask` treat an execution as superseded only if
`task.attempt != attempt`. Resuming a task with an expired lease sets it to `Created`, but the attempt is only
incremented when it is started again. If the old execution (alive, but its lease expired) finishes in that window,
`completeTask` passes the check and throws `InvalidBackgroundTaskStatus` (`requireIsRunning`). As `closeCompleted` runs
inside the handler's `try` in `TaskExecution.executeHandler`, this ends in `executeFailure`: `onFailure` is invoked for
a successful handler, and `failTask` (`Created` isn't closed) marks the resumed task `Failed`. The new launch is then
skipped as not ready, so the resume is lost. `supersededExecutionDoesNotChangeTask` only covers the case after attempt 2
started.

**Proposal:** Superseded if `attempt != null && (task.attempt != attempt || task.status.isReady)` in both methods (not
`isOwnedBy`, as a task canceled concurrently by the service must still be reported as closed). Possibly move
`closeCompleted` out of the handler's `try`. Test the window in `supersededExecutionDoesNotChangeTask`.

**Decision:** Accept proposal, amend test

**Implemented:** `BackgroundTaskLifecycleManager.isSupersededFor(attempt)` (`attempt != null && (task.attempt !=
attempt || status.isReady)`) in `closeIfOwned` and `cancelTask`. `supersededExecutionDoesNotChangeTask` covers the
window between resume and restart (complete, fail, cancel and sync of attempt 1 are superseded).

### A-16 - Scratchpad keys case-insensitive on MySQL/MariaDB

`medium` - not breaking

`data_key varchar(255)` uses the default collation, which is case-insensitive (and pads trailing spaces) on
MySQL/MariaDB, while the scratchpad cache and the duplicate item-key check are case-sensitive. Keys differing only in
case (`Readme`/`README`, e-mail addresses) share one row: the second `put` updates the first key's row, and on resume
the first key restores the wrong value and the second item runs again.

**Proposal:** Binary collation for `data_key` on MySQL/MariaDB (`modifySql` with `COLLATE utf8mb4_bin`), or store a
hash of the key (with the key in a separate column).

**Decision:** Use binary collation for `data_key`, increase column length to 1024 to be more lenient with keys

**Implemented:** `data_key` is `varchar(1024)` (`COLLATE utf8mb4_bin` on MySQL/MariaDB, changelog property
`kiwi.background-task.data-key-type`), `MAX_KEY_LENGTH = 1024`. As a unique index on `(task_id, data_key)` exceeds
MySQL's index key limit (3072 bytes, utf8mb4 takes up to 4096), uniqueness is enforced on the new column
`data_key_hash` (SHA-256, hex): `uq_kiwi_background_task_data_key (task_id, data_key_hash)`; lookups and deletes by key
use the hash (`BackgroundTaskData.hashKey`). Test: `scratchpadKeysAreCaseSensitive` (MariaDB).

**Overridden:**: Reverted `data_key_hash` decision, returned to 255-char scratchpad keys with `utf8mb4` collation.

### A-17 - Task handle disclosed by enqueue/control errors

`medium` - not breaking

**Implemented:** `TaskEnqueueFailed`, `TaskControlFailed` and `UnknownTaskHandle` don't have the argument

### A-18 - RabbitMQ: duplicate delivery unbinds task control

`medium` - not breaking

`RabbitBackgroundTaskQueue.handleTaskLaunchMessage` declares the task-control binding and overwrites

### A-20 - Dead-lettered launches can't be resumed

### A-26 - `retryWithBackoff`: off by one, unvalidated

`low` - not breaking

`BackgroundTaskHandler.retryWithBackoff(context, baseDelay, maxAttempt, exponent, maxDelay)` (added in `f984bd1`):

- `context.attempt > maxAttempt` retries after attempt `maxAttempt` too: With `maxAttempt = 3`, the task runs up to 4
  times. If `maxAttempt` is the last attempt allowed, the check must be `>=` (and the parameter could be named
  `maxAttempts`).
- The delay is `baseDelay * exponent^attempt`: The first retry (after attempt 1) waits `2 * baseDelay` with the default
  exponent, so `baseDelay` itself is never used; usually `exponent^(attempt - 1)`.
- No validation: A negative `baseDelay`, an `exponent < 1` or a `maxAttempt < 1` are accepted. Without `maxDelay`, the
  delay overflows to `Long.MAX_VALUE` milliseconds for large attempts (`Duration.ofMillis` of a saturated `Double`),
  which may overflow when added to the current time by a future retry scheduler.
- Manual resumes increment `attempt` as well, so they consume the retry budget (probably intended, worth documenting).
- Retries aren't supported yet (Q-03: the task fails regardless, `TaskExecution` logs the requested retry), and there
  are no tests; the KDoc doesn't mention either.

**Proposal:** `context.attempt >= maxAttempts`, delay `baseDelay * exponent^(attempt - 1)` capped by `maxDelay`,
`require` valid arguments, KDoc noting that retries aren't executed yet, unit tests with the
`InMemoryBackgroundTaskContext` (F-06).

**Decision:** Done

**Implemented (with F-09, as proposed):** Parameter renamed to `maxAttempts` (`>=`), delay
`baseDelay * exponent^(attempt - 1)` capped by `maxDelay` (saturates at `Long.MAX_VALUE` ms, the worker caps it),
`require`s for negative delays, `maxAttempts < 1`, `exponent < 1`; KDoc with an example and the note on resumes.
`FailureResponse` rejects negative delays. Tests: `BackgroundTaskHandlerTest` (api).

Revised by the author before review (2026-11-13): The function is split into two extension functions of the
`BackgroundTaskContext`, composable in `onFailure`:

- `context.retryWithBackoff(baseDelay, exponent = 2.0, maxDelay = null)`: The delay only (always retries).
- `context.limitRetries(maxAttempts) { ... }`: `noRetry()` once `attempt >= maxAttempts`, the block's response
  otherwise, e.g. `context.limitRetries(maxAttempts = 3) { retryWithBackoff(Duration.ofSeconds(10)) }`.

Fixed in review: A zero `baseDelay` returned `0 * Infinity = NaN` for very high attempts (rounding it threw), it now
stays zero (`backoffWithoutBaseDelayStaysZero`).

### Q-08 - Uncapped workers

`low` - not breaking

Requested: Investigate whether an "uncapped" worker (no limit of concurrent tasks) is possible, and its implications.

**Findings:**

- Technically possible for `cached-thread-pool` and `virtual-threads` (e.g. `max-concurrent-tasks: unlimited`,
  executors as before F-07); meaningless for `single-thread` and `fixed-thread-pool`.
- **RabbitMQ:** The prefetch count is the only flow control. "Unlimited" would be prefetch `0` (no limit): The broker
  pushes *all* pending tasks of a category to the first worker consuming it, no load balancing between instances, an
  instance started later gets nothing until new tasks arrive. All of them stay unacknowledged until executed, and are
  redelivered at once if the instance stops. A large finite prefetch has the same effect in moderation.
- **Local queue:** Already unbounded before F-07 (tasks queue in the worker), so uncapped only changes how many run at
  once.
- **Resources:** Each running task has a supervisor (a virtual thread, syncing progress and renewing its lease every
  third of the lease duration), and uses a database connection for its transactions. With hundreds of concurrent tasks,
  the connection pool (Hikari default 10) becomes the limit: Transactions wait for connections, lease renewals may be
  delayed beyond the lease duration, and tasks are reported as orphaned and may be resumed concurrently (aborted later
  as superseded). `cached-thread-pool` would create one platform thread per task (memory, `unable to create native
  thread`). Downstream systems (mail servers, APIs) see unbounded load.
- **Shutdown:** All running tasks are aborted at once after the shutdown timeout.

**Proposal:** Don't add "uncapped". Virtual threads with a high `max-concurrent-tasks` (sized by the connection pool and
downstream systems) cover I/O-bound tasks. If needed, a separate cap for the RabbitMQ prefetch could be considered.

**Decision:** Discard the idea of uncapped workers

Rejected: No change, `max-concurrent-tasks` stays required (default `1`).

## 7. Retries (F-09 to Q-12)

Requested on 2026-11-12 as the final feature before the release: Retrying failed tasks after a delay, as requested by

### F-09 - Retry failed tasks after a delay

`high` - not breaking (API extended: status `RetryScheduled`, `BackgroundTaskDetails.retryOn`)

Requested:

- Handlers decide whether a failed task is retried, by the `FailureResponse` returned by `onFailure`.
- A task eligible for a retry is put back into the queue: With RabbitMQ, into a separate retry queue, with a message
  expiration of the retry delay, from which it is dead-lettered back onto the task-launch queue.
- With the local queue, a scheduled executor service schedules the retries.
- Workers pick up the re-enqueued task and execute it again.

**Proposal:**

*Status model.* A new pending status `RetryScheduled` (`isPending = true`), instead of `Failed` (closed: clients would
see a final failure, statistics count it) or `Launched` (indistinguishable from a fresh launch, no retry time):

```
Running --> RetryScheduled : handler threw, onFailure requested a retry
RetryScheduled --> Running : picked up by a worker after the delay (next attempt)
RetryScheduled --> Failed : re-enqueueing failed
RetryScheduled --> Canceled : cancel
RetryScheduled --> Created : resume (retry now)
```

- New column `retry_on` (in the `createTable` of the 1.5.1 changelog, moved there by the author; first implemented as
  a new changeset `background-task-retry`): When the retry is due,
  `null` otherwise. The task keeps the error of the failed attempt (`error_data`) while waiting, and clears it (and
  `retry_on`) when the next attempt is started. `started_on` is cleared like on resume, so a task waiting for a retry
  counts as not started.
- Like a failure, the scratchpad and progress are retained: The retry is an ordinary next attempt, so stages and
  checkpoints skip completed work (the same mechanism as resuming, F-04).
- Domain event `BackgroundTaskRetryScheduled` (exception, delay); client message `StatusChanged.RetryScheduled`
  (`error`, `attempt` of the failed attempt, `retryOn`); `BackgroundTaskDetails.retryOn`.

*Who re-enqueues.* The queue, not the worker: `BackgroundTaskWorker.submit` completes its future with an
`ExecutionOutcome` (`Executed`, or `Retry(delay)` once the task has been marked `RetryScheduled`), and the queue that
delivered the task re-enqueues it. The worker stays unaware of the transport (no queue dependency, no cycle), and the
RabbitMQ queue publishes the retry *before* acknowledging the launch message, so a crash in between redelivers the
task instead of losing it. If re-enqueueing fails, the queue rejects the task via the worker (`worker.reject`,
reason `retry-failed`): A task still waiting for its retry fails, and can be resumed.

*Local queue.* A single-thread `ScheduledExecutorService` (daemon) runs `enqueueLaunch` after the delay, to a random
worker accepting the category, like a launch. Scheduled retries are lost when the process stops (like launched tasks
that haven't been started), and stay `RetryScheduled`, see Q-12.

*RabbitMQ queue.* Per category, a retry queue `<taskRetryQueue>.<category>` (new property
`queue.rabbit-mq.task-retry-queue`, default `retry_task`), bound to the exchange, without consumers, with
`x-dead-letter-exchange = <exchange>` and `x-dead-letter-routing-key = <taskLaunchQueue>.<category>`. A retry is
published to it with the message expiration set to the delay (milliseconds), with publisher confirms like a launch;
once expired, the broker dead-letters it to the category's launch queue. A zero delay is published to the launch queue
directly. Per-message expiration has a caveat, see Q-09 (*superseded by the Q-09 decision: delayed messages in the
launch queue, RabbitMQ 4.4+*).

*Worker.* `TaskExecution` asks `onFailure` (as before), and if it requests a retry, marks the task `RetryScheduled`
instead of `Failed` (`BackgroundTaskLifecycleManager.scheduleRetry`, only if the execution still owns the task).
The delay is capped by the new property `worker.max-retry-delay` (default `1d`), negative delays count as zero.
No retry for: failures of `onFailure` itself, `Error`s, cancellations, superseded executions. A worker shutdown
(`BackgroundTaskWorkerShutdown`) invokes `onFailure` as before, so a handler may retry an aborted task on another
worker.

*Management and statistics.* `RetryScheduled` tasks are listed by default and are resumable ("retry now", also the
remedy for a lost retry, Q-12). Stats: `pending` stays `Created` + `Launched` (a task waiting for its retry is not
waiting for a worker), new figure `oldestRetryOn` (earliest due retry: far in the past means retries are lost).

*`retryWithBackoff` (A-26).* Fixed with this feature, as it is the main API for retry delays: `maxAttempts` (the task
runs at most that often), delay `baseDelay * exponent^(attempt - 1)` capped by `maxDelay`, arguments validated. (Since
split into `context.retryWithBackoff(baseDelay, exponent, maxDelay)` and `context.limitRetries(maxAttempts)`,
see A-26.)

**Decision:** Done

### Q-09 - RabbitMQ: retry delays block each other

`medium` - not breaking

RabbitMQ expires (and dead-letters) messages only at the head of a queue. With per-message expirations in one retry
queue, a retry with a long delay at the head holds back retries with shorter delays behind it: With exponential
backoff, task A waiting 10 minutes for its third attempt delays the first retry (1 second) of task B by up to
10 minutes. Delays are therefore *minimums*. The impact is limited per category, as each category has its own
retry queue.

Options:

1. **Accept and document** (implemented): Delays are minimums; use similar delays per category, or separate
   categories for very different delays.
2. **Delay tiers:** A retry queue per delay tier with a queue TTL (`x-message-ttl`), e.g. 1s, 10s, 1m, 10m, 1h; the
   delay is rounded up to the next tier. FIFO per queue, no blocking, a fixed number of queues. Changes the requested
   delay slightly, more topology.
3. **Delayed-message exchange plugin** (`rabbitmq_delayed_message_exchange`): Exact delays, but an extra broker
   plugin with known limitations (delayed messages are kept on a single node, not replicated).

**Proposal:** 1 for this release; 2 if the blocking matters in practice.

**Decision:** Replace the TTL and dead-letter logic with the native delayed messages of RabbitMQ 4.4+
(`x-opt-delivery-time`). On startup, ensure the queue is a quorum queue, and query the broker whether the feature is
supported, if possible (e.g. minimum RabbitMQ version, or similar detection, if not too complicated or costly).

**Implemented:** As decided.

- RabbitMQ 4.4 supports delayed messages in quorum queues: A message with the header `x-opt-delivery-time` (AMQP 0-9-1:
  `long`, absolute epoch milliseconds) is enqueued immediately, but delivered only once that time is reached,
  independently of other delayed messages (no head-of-line blocking). No plugin, exchange type or queue argument is
  needed; delayed messages count toward the queue's length limit.
- Task-launch queues are declared as durable quorum queues (`x-queue-type: quorum`). If a launch queue exists with
  another type (e.g. a classic queue of an earlier version) or arguments, the declaration fails with
  `PRECONDITION_FAILED`, and initialization fails with a hint to drain and delete the queue.
- A retry is published to the category's launch queue with `x-opt-delivery-time = now + delay` (by the instance's
  clock), without the header for a zero delay. The retry queues and the property `queue.rabbit-mq.task-retry-queue` are
  removed, as are the category properties `durable` and `auto-delete` (quorum queues are always durable and never
  auto-deleted; unknown properties are ignored by the binding).
- Support detection: On initialization, the queue reads the broker version announced on connection (server property
  `version`, no management API needed). Older than 4.4 → initialization fails (`IllegalStateException`); unknown or
  unparseable (e.g. another broker product) → warning, continue. On failure, the partially initialized queue is
  destroyed (stops the worker-control listener).
- A full launch queue now rejects a retry when it is published (nack → `retry-failed`, task fails and can be resumed),
  instead of the broker dropping it when dead-lettering (Q-12 updated).
- Tests: `rabbitmq:4.4` container image (was `latest`). `RabbitBackgroundTaskQueueTest`: `retryIsDelayed` (not
  delivered before the delay, delivered after it, nothing dead-lettered), `retryIsNotHeldBackByLongerRetries` (a retry
  of 300 ms is delivered while a retry of 1 minute waits ahead of it), `launchQueueOfAnotherTypeFailsInitialization`;
  `fullQueueRejectsLaunch` adjusted. `RabbitBrokerVersionTest`: version parsing (`4.4.0`, `4.4.0-rc.1`,
  `4.5.2+12.gabcdef`, `4.10.0`, `5.0.0`, `4.3.7`, `3.13.7`, unknown).
- Docs: RabbitMQ 4.4 requirement, quorum queues (migration: drain and delete classic launch queues), delayed retries,
  properties table.

Remarks:

- Not breaking for framework consumers (the module is unreleased), but existing development or test brokers have
  classic launch queues, which must be drained and deleted; brokers before 4.4 are refused.
- A quorum queue rejects messages (`reject-publish`) once it *exceeds* its maximum length, i.e. it holds
  `max-queue-length + 1` messages (observed with 4.4.0; classic queues held exactly `max-queue-length`). Documented.
- Quorum queues have a delivery limit (`x-delivery-limit`, default 20 since RabbitMQ 4.0): A launch message returned
  more often (e.g. requeued by repeatedly crashing or stopping workers) is dead-lettered. Not changed, not tested.
- A clock skew between the instance and the broker shifts the delay. The version check only sees the node the instance
  is connected to (e.g. not a mixed-version cluster during a rolling upgrade).

### Q-10 - Canceling a task waiting for its retry

`low` - not breaking

Canceling a `RetryScheduled` task cancels it immediately (not running, no worker signaled). The A-21 decision invokes
`onCancel` only for tasks that have never been started; a task waiting for its retry has been started before (and
`onFailure` has been invoked for the failed attempt), so `onCancel` is not invoked.

Since the retry's launch message is only delivered after the delay, the worker broadcasts `Canceled` when it picks it
up, i.e. clients receive the `Canceled` message after the delay (the cancel request and the task details reflect it
immediately). Stale messages of tasks canceled while running are still skipped silently (the worker distinguishes them
by `started_on`, which is cleared while waiting for the retry).

**Proposal:** As implemented. Alternatively invoke `onCancel` for canceled retries as well (the handler may want to
clean up after the failed attempt).

**Decision:** Keep as is, don't invoke `onCancel` if retry-scheduled task is canceled

**Implemented:** As decided (no code change). Chapter 10 "Canceling a task" documents it (no `onCancel`, `Canceled`
broadcast when the retry would have been due); the possible second `Canceled` message after resuming (Q-13) is noted
in "Resuming Tasks". Covered by `taskWaitingForRetryIsCanceled` (integration, local and RabbitMQ).

### Q-11 - Safety net against endless retries

`low` - not breaking

A handler returning `retry()` unconditionally retries forever, with a zero delay as fast as the workers execute it.
The module doesn't limit the attempts; `context.retryWithBackoff` doesn't limit them either, the handler wraps it in
`context.limitRetries(maxAttempts) { ... }` (optional).

**Proposal:** No limit in the module for now (the handler decides, as requested), documented as a best practice.
Possible addition: a property `worker.max-attempts` overriding retries beyond it, and/or a minimum delay.

**Decision:** Document as best practice, try and hope developers think before they code.

**Implemented:** As decided (no code change). Chapter 10 "Retrying Failed Tasks" ("Limit the attempts") and the best
practice "Retry transient failures only, and limit the attempts" (`retryWithBackoff` within `limitRetries`).

### Q-12 - Lost and early retries

`low` - not breaking

- **Lost:** A retry can be lost while the task is already `RetryScheduled`: The process stops (local queue), the
  instance crashes between marking the task and publishing the retry (RabbitMQ: the unacknowledged launch message is
  redelivered, see below). The task then stays `RetryScheduled`. (With the delayed messages of Q-09, a full launch
  queue rejects the retry when it is published, so the task fails instead; the former loss when dead-lettering an
  expired retry into a full launch queue no longer applies.)
  Remedy: `RetryScheduled` tasks are resumable, and `oldestRetryOn` in the stats reveals overdue retries.
- **Early:** If an instance crashes after publishing the retry but before acknowledging the launch message, the launch
  message is redelivered, and a worker starts the `RetryScheduled` task right away (it is pending); the delayed retry
  is skipped later. Waiting for `retry_on` instead would require re-queueing the message (busy redelivery) or
  dropping it (risking a lost retry).

**Proposal:** As implemented (at-least-once, delays are minimums except after a crash). Automatic recovery of overdue
retries could be part of the orphan recovery (I-01, deferred).

**Decision:** Keep at-least-once as implemented, leave recovery to monitoring/administration

**Implemented:** As decided (no code change). Chapter 10 "Retrying Failed Tasks" ("Retries are at-least-once") now
names both loss cases (local process stop, crash before publishing to RabbitMQ), states that lost retries aren't
recovered automatically, and points to `oldestRetryOn` (statistics table: alert threshold) and resuming.

### Q-13 - Stale retry after resuming a task waiting for it

`low` - not breaking

Found in the review of the staged retry changes (2026-11-13). Resuming a `RetryScheduled` task ("retry now") enqueues
a new launch message, but the pending retry stays scheduled: With RabbitMQ, its delayed message stays in the launch
queue; with the local queue, its scheduled job still fires. When the stale retry is delivered at its due time:

- The task is running, completed, failed or canceled by then: It is skipped (as intended), or canceled while pending:
  `Canceled` is broadcast a second time (see Q-10).
- The task waits for a retry *again* (the resumed attempt failed, and its handler requested another retry with a later
  `retry_on`): The stale retry is picked up, and the next attempt starts **early**, before its delay. The proper retry
  is skipped later.

Tasks are never executed concurrently (starting a task is guarded by its status), so the effect is an early attempt (and
a duplicate `Canceled` message), not a duplicate execution. The same applies to resuming a `RetryScheduled` task
twice, or to the early retries of Q-12.

Options:

1. **Accept and document** (documented in chapter 10, "Resuming Tasks"): Retries are at-least-once, delays are
   minimums except after resuming or a crash.
2. **Skip early deliveries:** The worker skips (acknowledges without starting) a delivery while the task is
   `RetryScheduled` and `retry_on` is clearly in the future (beyond a tolerance for clock skew): The due retry is still
   pending. Downside: In the crash window of Q-12 (task marked `RetryScheduled`, but the retry not published yet), the
   redelivered original launch message is the only one left, so the retry is lost (the task stays `RetryScheduled`,
   revealed by `oldestRetryOn`, resumable).
3. **Tag launch messages with the expected attempt:** The retry message carries the failed attempt; a worker skips it
   if the task's attempt differs (i.e. it has been resumed or retried since). Precise, but extends the message format
   (`LaunchTaskBody` and the local queue's submission), and the original launch message of Q-12 still needs option 2.

**Proposal:** 1 for this release (the effect is rare and harmless for idempotent handlers); 2 if early attempts matter
in practice.

**Decision:** Accept and document this edge-case for now

**Implemented:** As decided (no code change). Chapter 10 "Resuming Tasks" documents the stale retry (delivered when due,
early next attempt if the task waits for a retry again, possible second `Canceled` message); "Retries are
at-least-once" links to it.
