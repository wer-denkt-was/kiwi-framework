## 1. Spring Boot 4 upgrade (U)

**State (2026-10-22):** U-01 to U-10 are implemented and committed (`b0ad96b`).
`./gradlew clean build` was green with 219/219 tests passing and none skipped, the same tests as the baseline.
Javadoc/Dokka jars build. Liquibase migrations run (todo-app validates its schema with `ddl-auto: validate`).

### U-01 - Version upgrades

`high` - breaking

- Spring Boot 3.5.14 → **4.1.1**, which brings Spring Framework 7.0.9, Spring Security 7.1.1, Spring Data 2026.0.1,
  Hibernate 7.4.5, Jakarta Persistence 3.2, Jackson 3.1.5 (plus Jackson 2.21.5 for libraries), Testcontainers 2.0.5
  and JUnit 6.0.3.
- Kotlin 2.2.21 → **2.3.21**, the version managed by the Boot 4.1.1 BOM.
- springdoc-openapi 2.8.14 → **3.1.1**, built against Boot 4.1.0.
- Unchanged: Dokka 2.1.0, Gradle 9.6.0, dependency-management plugin 1.1.7, jjwt 0.12.6.
  See [Q-05](#q-05---remaining-items-from-the-wip-stash) for further bumps.

### U-02 - Dependency coordinates

`high` - breaking (consumers need the same changes)

- Starters: `spring-boot-starter-web` → `-webmvc`, `spring-boot-starter-json` → `-jackson`.
- Test slices need per-technology test starters: `spring-boot-starter-data-jpa-test`, `spring-boot-starter-webmvc-test`.
- **`org.liquibase:liquibase-core` → `spring-boot-starter-liquibase`**. Liquibase auto-configuration moved into its

- `hibernate-jpamodelgen` → `org.hibernate.orm:hibernate-processor`, since the BOM no longer manages the old name.

- `spring-boot-security` added: `compileOnly` and test scope in bundle. It is needed for `EndpointRequest` in
  `KiwiManagementSecurityConfig`, and for the security auto-configurations that tests exclude.
- `api` gets `compileOnly("org.hibernate.orm:hibernate-core")`
  for [U-07](#u-07---hibernate-7-subtype-attribute-resolution).

### U-03 - Jackson 3 migration

`high` - breaking. Public signatures expose `JsonNode`/`ObjectMapper`, for example `GenericEntityCommand.jsonBody`
and `Fieldset.extractJson`.

- Packages `com.fasterxml.jackson.{core,databind,module}` → `tools.jackson.*`. Annotations stay in
  `com.fasterxml.jackson.annotation`.
- `EntityIdJsonModule`: `ValueSerializer`/`ValueDeserializer`, `SerializationContext`, `BeanDescription.Supplier`,
  `writeName`, `JsonParser.string`.
- Bean introspection moved from `DeserializationConfig` to `DeserializationContext`. New internal helpers are in
  `bundle/.../support/JacksonIntrospection.kt`.
- Immutable mappers: `registerModule` → `jacksonMapperBuilder().addModule(…).build()`. `JavaTimeModule` is built in now.
- Renames: `TextNode` → `StringNode`, `textNode` → `stringNode`, `asText` → `asString`, `fieldNames()` →
  `propertyNames()`, `TypeFactory.defaultInstance()` → `createDefaultInstance()`, `JsonMappingException` →
  `DatabindException`, `NamingBase.translate` is protected now (`nameForField` is used instead).
- **Kept on Jackson 2:** `KiwiOpenApiConfig.kt:676`, because swagger-core (springdoc 3) still passes Jackson 2
  `JavaType`s.
- **Pitfall for consumers:** Jackson 3 `JsonNode.map(Function)` transforms the node *itself*. In Kotlin this member
  takes priority over the `Iterable.map` extension, so `node.map { … }` silently changes meaning. The codebase was
  searched for this, and one test was affected. Use `node.values().map { … }`. To be included
  in [U-11](#u-11---consumer-migration-guide--release-notes).

**Decision:** _pending_

### U-05 - JSpecify nullness (Spring Framework 7 / Spring Data 4)

`high` - breaking (signature changes)

Spring 7 and Spring Data 4 are JSpecify-annotated, and Kotlin enforces this strictly. The following public API
signatures changed:

- `QueryBuilder.Executor<R : Any>`, `PageResult.fromPage<T : Any>`, `QuerySchemaService.findPage<E, N : Any>`.
  Spring Data `Page<T>` requires a non-null `T`.
- `AccessControlSpecification.toPredicate(…, query: CriteriaQuery<*>, …)` and `and`/`or(other: Specification<E>)`
  are non-null now, and so is `GenericEntityFilter.toPredicate`.
- `AuthenticationUserDescriptorConverter`, see [Q-04](#q-04---nullable-authenticationuserdescriptorconverter).
- Internal: `QuerySchemaEngine` paging moved to a bounded extension, so that `findOne`/`findAll` still accept nullable
  node types such as `BasicFieldsetSerializer`. `GrantedAuthority.authority` is nullable now
  (`LocalFileStorageService`). `HttpHeaders` no longer implements `MultiValueMap`.

**Decision:** _pending_

`high` - breaking (behaviour of plain `Specification`s,
see [Q-02](#q-02---plain-specifications-in-access-control-subqueries))

`Specification.toPredicate` no longer accepts a null `CriteriaQuery`. Previously `lift()` passed `null` when access

- `lift()` (`AccessControl.kt:382`) throws an `IllegalStateException` with a clear message if a plain third-party
  `Specification` is applied within a subquery.
- `demo/access-control-tests` passes unchanged.

### U-07 - Hibernate 7 subtype attribute resolution

`high` - not breaking (behaviour preserved)

Hibernate 7 no longer resolves attributes declared on a *subclass* via a supertype path
(`PathElementException: Could not resolve attribute 'isbn' of Publication`). The KDoc of `SubtypeField.treatFrom`
(`EntitySchema.kt:794`) had predicted this. Hibernate 7 offers the lookup explicitly instead:

- `Path<*>.getIncludingSubtypes(name)` (`JpaExtensions.kt:58`) uses `SqmPath.get(name, includeSubtypes = true)`. It
  is used by `ColumnSelector`.
- `joinIncludingSubtypes` (`JpaExtensions.kt:135`) resolves the singular attribute with subtypes included and joins
  it by attribute. It is used by `reusableJoin`.
- Both fall back to standard JPA if Hibernate is absent. **Open:** plural (collection) attributes declared on subtypes
  still use a plain join by name.

**Decision (2026-10-27, by the user):** Use a consistent mechanism in accordance with Hibernate 7 for plural attributes
declared on subtypes, too.

**Implementation (2026-10-27):** `joinIncludingSubtypes` (now public in `JpaExtensions.kt`) resolves the attribute
including subtypes, and joins singular and plural (`Set`, `List`, `Map`, `Collection`) attributes by the resolved
attribute; it is also used by `CriteriaAccessControl.crossCorrelatedJoin(name)`. Test: `Book.keywords` element
collection and `JpaQuerySchemaServiceTest.joinSubtypeAttributes` (fails without the fix with
`Could not resolve attribute 'keywords' of Publication`).

### U-09 - kapt stubs and JSpecify delegation

`medium` - not breaking

- Kotlin `by` delegation to `Specification` made kapt generate invalid Java stubs, placing a type-use `@Nullable` on a
  qualified type. It is replaced by an explicit override in `GenericEntityFilter.ValueAndSpecification`
  (`GenericEntityFilter.kt:123`). Avoid `by` delegation to JSpecify-annotated Spring interfaces in kapt-enabled modules.
- kapt hides javac diagnostics ("Error while annotation processing" with no message). Workaround for debugging:
  replay javac over `build/tmp/kapt3/stubs` with the kapt processor path.
- Hibernate Processor 7 generates metamodels for `EntityId` subclasses, so these classes must not be `private`. This
  affected the fixtures in `BaseEntityTests`.

**Decision:** _pending_

### A-02 - Adopt SpringBoot autoconfiguration

`high` - breaking

- Consumers `@Import(KiwiFrameworkConfiguration, KiwiAuditLogConfiguration, KiwiStorageConfiguration)` and must add
  bare `@EntityScan`/`@EnableJpaRepositories` themselves (`docs/01-introduction.md`, `DemoApplication.kt`).
- The library uses `@ComponentScan` (`KiwiFrameworkConfiguration.kt:36`, `KiwiStorageConfiguration.kt:30`), as well
  as `@EntityScan` and `@EnableJpaRepositories` (`KiwiStorageConfiguration.kt:31-32`,
  `KiwiAuditLogConfiguration.kt:25-26`).
  These disable Boot's default scanning of the host application.
- `@ConditionalOnBean` inside regular `@Configuration` classes depends on registration order
  (`KiwiRouterFunctionConfig.kt:26,54`, `KiwiOpenApiConfig.kt:77,90`).
- Only a few beans can be overridden via `@ConditionalOnMissingBean`: bundle 4/38, storage 2/4, audit-log 0/2,
  mjml 0/2. Not replaceable, for example: the buses, `querySchemaService`, `genericHandlerProvider`, mail,
  `ExceptionResponseManager`.

**Proposal:** `@AutoConfiguration` classes with imports files per module. Register entity and repository packages
via `AutoConfigurationPackages`/`EntityScanPackages` instead of scanning annotations. Use `@ConditionalOnMissingBean`
on all replaceable beans, add opt-out properties, and keep `@Import` working for a transition period if wanted.

**Decision:** Accepted, rewrite will be performed.

**Implementation:** Each module registers its auto-configurations in
`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`:

- framework: `KiwiFrameworkAutoConfiguration` (core), `KiwiBusAutoConfiguration`, `KiwiMailAutoConfiguration`,
  `KiwiWebAutoConfiguration` (servlet only), `KiwiOpenApiAutoConfiguration` (if springdoc is present),
  `KiwiManagementSecurityAutoConfiguration`
- audit-log: `KiwiAuditLogPackagesAutoConfiguration`, `KiwiAuditLogAutoConfiguration`
- storage: `KiwiStoragePackagesAutoConfiguration`, `KiwiStorageAutoConfiguration`
- mjml: `KiwiMjmlAutoConfiguration`

Details:

- No `@ComponentScan`, `@EntityScan` or `@EnableJpaRepositories` in library configurations anymore. The former
  `@Component`s (method handlers, route helper, OpenAPI helper, controller advice, `FileEntityService`,
  `LocalFileController`) are `@Bean`s. The remaining internal configuration classes are `@Import`ed by the
  auto-configurations, so their conditions are evaluated in autoconfiguration order.
- Entities: `Kiwi*PackagesAutoConfiguration` registers the entity package as autoconfiguration package, and as
  entity-scan package if the application declares `@EntityScan`. It is ordered *before* the JPA auto-configurations,
  because `DataJpaRepositoriesAutoConfiguration` instantiates the autoconfiguration packages while registering
  repositories, after which additional packages are silently ignored.
- Repositories: a nested `@EnableJpaRepositories(basePackageClasses = [...])` with `@ConditionalOnMissingBean(<repo>)`,
  ordered *after* the JPA auto-configurations. The repository package is deliberately not registered as an
  auto-configuration package: Spring Data registers repositories of overlapping packages twice
  (`BeanDefinitionOverrideException`, seen in the storage integration test).
- `ClassPathScannerUtil` (schemas, generic commands, reports) and the dev tooling (`CommandQueryVerification`,
  `FieldsetSourceGeneratorTool`) read entity-scan and autoconfiguration packages, instead of only `@EntityScan`
  annotations, so Kiwi module schemas (e.g. `FileSchema`) are still found. `SpringQuerySchemaProvider` now skips
  non-public schema/fieldset classes with a warning (test packages contain `private object` schemas).
- `@ConditionalOnMissingBean` on all replaceable beans (interface return types where relevant). The command and query
  bus conditions ignore `CommandQueryBus`, see A-17.
- Opt-out: `kiwi.web.enabled`, `kiwi.web.open-api.enabled`, `kiwi.mail.mjml.enabled`, `kiwi.audit-log.enabled`, and
  `spring.autoconfigure.exclude` in general. `KiwiManagementSecurityAutoConfiguration` is ordered before Spring Boot's
  web security auto-configurations, like the former regular configuration.
- No transition `@Import` support: the classes were renamed, so outdated `@Import`s fail at compile time.
- `transactionService` is only created if a `PlatformTransactionManager` exists; the buses fall back to `DoNothing`.
- The demo app needs no `@Import`/`@EntityScan`/`@EnableJpaRepositories` anymore. Slice tests (`@DataJpaTest`,
  `@WebMvcTest`) disable `@EnableAutoConfiguration`, so they use `@ImportAutoConfiguration` of the Kiwi
  auto-configurations, e.g. `AccessControlTest` (explicit `@EntityScan`/`@EnableJpaRepositories` path).
- Tests: `KiwiFrameworkAutoConfigurationTest`, `KiwiAuditLogAutoConfigurationTest`, `KiwiStorageAutoConfigurationTest`
  (default packages, explicit packages, overrides, opt-out properties, provider selection).

### A-06 - `GlobalSingleton` and other static state

`high` - quick fix not breaking, full fix breaking

### A-08 - Bus thread-safety and handler cache

`medium` - not breaking

- `register` is synchronized, but `findHandler` iterates the plain `ArrayList` without a lock
  (`BasicCommandBus.kt:19-29`). The event and query buses work the same way.
- `HandlerCache` is never invalidated: a handler registered after first use is silently missed. `hitRate()` returns
  `NaN` before the first lookup (`HandlerCache.kt:24`).
- `EventRecursionDepthExceeded` extends `Exception` (`RecursiveEventBus.kt:38`).
- The decorator chain is fixed, and there is no interceptor SPI.

**Decision:** Fix synchronization, invalidate handler-cache on application reload or when appropriate. Decorator chain
will be revisited later; see `I-04`.

**Implementation:** Handlers/subscribers are kept in `CopyOnWriteArrayList`s (lock-free lookups). Registering a handler
or subscriber invalidates the `HandlerCache`; invalidation replaces the cache map, so a concurrent lookup cannot store a
stale entry. A restarted application context creates new buses, so no further reload handling is needed.
`hitRate()` returns `0.0` before the first lookup. Test: `EventBusTest.subscribeAfterPublishInvalidatesCache`.
`EventRecursionDepthExceeded` extends `RuntimeException` now, with a message (decided 2026-10-22). As a checked
`Exception`, Java callers could not catch it (Kotlin declares no `@Throws`), and `TransactionTemplate` wrapped it in an
`UndeclaredThrowableException`. `Error`/`AssertionError` were ruled out, as they bypass the `Exception` handlers (see
A-05); `IllegalStateException` as well, as it is mapped to 400. **Open, with A-05:** `EventPublishingCommandBus`
rewraps it into an `IllegalStateException` (400) without the cause; it should use the dedicated internal exception
type (500) and keep the cause.

### <a name="i-01">I-01</a> - Remove JWT support, replace local file-storage tokens

Kiwi should not provide built-in JWT support; token-service, its implementations, and the related
`Authorization: Bearer [...]` support should be removed entirely. The remaining usages of the token-service, i.e. the
file-storage service, should use a dedicated token-interface serving as an SPI with a default implementation.
Write a default implementation which generates a simple access-token containing a reference of the authorized file, an
expiration timestamp, and a signed HMAC. This token-service and its configuration should be scoped to the local
file-storage service.

**Decision:** Implement idea and rewrite codebase accordingly.

**Implementation:**

- Removed: `AuthenticationTokenService` (api), `JwtTokenService`, `BearerTokenAuthenticationFilter`,
  `KiwiFrameworkProperties.jwt` (bundle), and the jjwt dependencies.
- New SPI `LocalFileTokenService` (`generateToken(fileUuid, duration)`, `verifyToken(token, fileUuid)`), default
  `HmacLocalFileTokenService`: `base64url("v1:{uuid}:{expiresEpochSeconds}").base64url(HMAC-SHA256)`. The signature is
  checked in constant time before the payload is interpreted; secret keys must have at least 256 bits. Tokens are
  stateless, so instances sharing the key accept each other's tokens. Access is granted per file UUID, as before
  (sibling files share the UUID).
- Configuration: `kiwi.storage.local.token.secret-key` (Base64), required for `kiwi.storage.provider=local`. The bean
  only exists for the local provider and can be replaced. The clock comes from `ClockProvider`.
- Invalid or expired tokens now yield 403, before they raised a JWT exception.
- Tests: `HmacLocalFileTokenServiceTest`, `LocalFileStorageServiceTest` uses the real token service.

### <a name="i-05">I-05</a> - Audit-log event details as JSON column

### <a name="i-06">I-06</a> - Overhaul generic create/update/delete commands

Requested by the user (2026-10-26), **top priority**. The old system (`GenericCreate`, `GenericUpdate`, `GenericDelete`,
handlers with `CreateBody`/`UpdateBody`, `PatchCommand`) is commented out in the working tree in anticipation of the new
system; a WIP draft lives in `api/.../generic/GenericCreate.kt`.

**Problems of the old system:**

- The command classes declare no properties: which JSON keys are required, supported or ignored is only known by reading
  the handler code (`create.require(TodoItemSchema.title)`, `update.patchField(...)`). Nothing is statically checkable.
- No discoverable way to accept non-schema properties: handlers read them ad hoc (`create.require<Boolean>("x")`).
- Frontend code generation and the `_schema` metadata cannot know the body: `FieldsetSourceGenerator` declares *all*
  writable columns of the schema as optional, `GenericMetadataProvider` reports no properties at all for generic
  commands, and the OpenAPI request bodies are untyped. This caused repeated problems with generated create/update
  interfaces.

**Requirements (by the user):**

- Body properties are declared explicitly as `val «name» by «delegateFn»(...)`, deriving their value from the
  underlying `lateinit` JSON body.
- `by schema(FooSchema.x)` (`ColumnField`): parse like the old `CreateBody.get(ColumnField)` (JSON → mapped type `M` →
  `ColumnType.parse` incl. auto-validation → `T`; `EntityFieldWriteNotAllowed`/`EntityFieldInvalid` on failure).
- `by property<T>()`: parse a value of type `T` from the JSON key named after the delegated property.
- `by reference(FooSchema.parent)` (`ToOneField`): the primary `EntityId` type of the referenced entity, so the handler
  can resolve related entities.
- Update commands: patch logic, properties accessed conditionally iff their key is present, like `PatchCommand`.
- Further delegates may be proposed to make the system more flexible, intuitive or useful.

**Proposal (design):**

```kotlin
class CreateTodoItem : GenericCreate<TodoItem>() {
    override val entityFieldset = TodoItemFieldsets.default

    val list by reference(TodoItemSchema.list)              // TodoListId, required
    val title by schema(TodoItemSchema.title)               // String, required
    val content by schema(TodoItemSchema.content).optional() // String?, entity default if absent
    val notify by property<Boolean>().default(false)         // non-schema property

    override fun preAuthorize(user: UserDescriptor) = Unit
}

@Component
class CreateTodoItemHandler(private val lists: TodoListRepository) :
    GenericCreateHandler<CreateTodoItem, TodoItem>() {
    override fun createEntity(create: CreateTodoItem, user: UserDescriptor) = DomainResult { record ->
        val list = lists.requireById(create.list)
        user.requireAdminOrListAuthor(list)
        record(TodoItem.create(list, title = create.title, content = create.content ?: ""))
    }
}

class UpdateTodoItem : GenericUpdate<TodoItem, TodoItemId>() {
    override val entityFieldset = TodoItemFieldsets.default

    val title by schema(TodoItemSchema.title)    // all update properties are optional (patch)
    val status by schema(TodoItemSchema.status)
    val order by schema(TodoItemSchema.order)
}

// In GenericUpdateHandler.updateEntity(update: UpdateTodoItem, entity: TodoItem, user):
update.patchFields(entity, update::title, update::status)          // write present schema properties to the entity
update.ifPatched(update::order) { order -> record(entity.moveOrderInList(order)) }
```

- **Field registry:** the delegate functions return `PropertyDelegateProvider`s, which register a field descriptor
  (Kotlin property name, JSON key, kind, value type as `KType`/`JavaType`, required, nullable, source `ColumnField` or
  `ToOneField`) in the command when it is instantiated. Instantiating a command with its no-arg constructor (as the
  provider and code generator do already) yields the complete body description without any JSON: this is the single
  source for `_schema` metadata, OpenAPI request bodies and frontend interfaces.
- **Typing:** the property type follows the source: `schema(col)` returns the column's `T` (nullable iff the column is
  nullable), `property<T>()` returns `T` (required iff `T` is non-null), `reference(toOne)` returns the referenced
  entity's ID type (`R : BaseEntity<ID>`). Modifiers: `.optional()` (`T?`, key may be absent on create),
  `.default(value)`, `.validate(validation)` (for `property`), `.key("json-key")` (rename).
- **Further delegates:** `references(FooSchema.children)` for a `ToManyField` (`Set<ID>`), `json()` for the raw
  `JsonNode` of a key (escape hatch, described as "any"), and possibly `entityType()` for subtype creation (see open
  questions).
- **Binding:** the provider instantiates the command, assigns `jsonBody`, and binds it with the `ObjectMapper` before
  dispatching: all fields are parsed eagerly, so invalid or missing values fail with 400 before the handler runs, and
  unknown keys can be detected. Accessing a property reads the bound value.
- **Create semantics:** absent key or `null` → missing; a required field fails with `EntityFieldMissingValue`.
- **Update semantics:** absent key = not patched; `null` = patched to `null`, which fails for non-nullable fields
  (`EntityFieldMissingValue`, like `patchNotNull`). Reading an unpatched property directly fails; access via
  `ifPatched(::prop) { }`, `ifPatchedNotNull`, `patchFields(entity, ::props)` (schema fields only).
- **Delete:** `GenericDelete<E, ID>` keeps its shape (no body).
- **Handlers:** `createEntity`/`updateEntity` receive the typed command; `CreateBody`/`UpdateBody` are removed.
- **Startup validation:** the provider instantiates every generic command once and fails on invalid declarations
  (read-only column in `schema()`, duplicate JSON keys, reference target without a single `EntityId` primary key).

**Plan:**

1. Spike: delegate providers and type inference (`reference()` inferring `ID` from `R : BaseEntity<ID>`, nullable `T`
   from `ColumnField<E, T, M>`), field registry, binding; decide the open questions below.
2. API module: `GenericCreate`, `GenericUpdate`, `GenericDelete`, field descriptors and delegates, patch accessors;
   remove `PatchCommand` or base it on the same mechanism.
3. Handlers: `GenericCreateHandler`, `GenericUpdateHandler`, `GenericDeleteHandler`, `GenericModificationHandler`.
4. `SpringGenericHandlerProvider`: discovery, instantiation, binding, error mapping, startup validation; log line.
5. Consumers of the descriptors: `GenericMetadataProvider` (create/update properties), OpenAPI request bodies,
   `FieldsetSourceGenerator` (required/optional/nullable per create and update interface).
6. Demo app, test commands and examples (`GenericTestCommands`, `example/*Example.kt`); tests for parsing, required and
   optional fields, `null` handling, patch semantics, unknown keys, references, descriptors, code generation, OpenAPI.

   notes (U-11).

**Open questions:**

1. Patch access style: `ifPatched(::prop)` on plain-typed properties (as `PatchCommand`, same declarations as create)
   or a `Patch<T>` wrapper type (absence visible in the type, no accidental unconditional read)? Recommendation: the
   former.
2. JSON key of `schema()`/`reference()` fields: the Kotlin property name (as `property()`) or the schema field name (as
   the old `CreateBody`)? Recommendation: property name, with a startup warning if it differs from the field name.
3. Unknown JSON keys: reject with 400, ignore, or ignore with a debug log? Frontends often send read-only fields (`id`)
   back. Recommendation: reject, with an ignore list per command.
4. Parse timing: eager at binding (errors before authorization and handler) or lazy on access? Recommendation: eager.
5. Error reporting: first error, or aggregate all field errors in one 400 response?
6. Keep the annotation-based custom commands (`@CreateCommand`, `@UpdateCommand`, `@DeleteCommand`, Jackson
   deserialized)? They remain statically introspectable. Recommendation: keep.
7. Programmatic construction (tests, dispatching generic commands from code): public `bind(json, objectMapper)`, or a
   builder setting values per property?
8. `reference()` returns the ID only, or should the handler get a helper resolving the entity (with access control)?
9. Subtype entities: create commands choosing a subtype (`entityType()` delegate), or out of scope for 1.5.0?
10. Should create commands derive required fields from the entity constructor instead of explicit declarations?
    Recommendation: no, explicit declarations are the point of this change.

**Decision (2026-10-26, by the user):** Proceed with plan, design and implementation; open questions answered:

1. `ifPatched` if it allows a simpler migration, otherwise propose a `Patch<T>` wrapper type.
2. Schema field name as JSON key when a schema field is referenced; warn on startup if property and field name differ.
3. Reject unknown JSON keys.
4. Parse at binding time.
5. Report all errors in one 400 response.
6. Keep the custom commands as alternative.
7. Add a public `bind(json, mapper)` for internal dispatch and testing.
8. `reference()` only returns the ID; loading entities is the handlers' responsibility (commands contain plain data).
9. Support selecting a subtype.
10. No.

### <a name="i-07">I-07</a> - HTTP `PATCH` instead of `PUT` for updates

**Request (2026-10-27, by the user):** Replace HTTP `PUT` with HTTP `PATCH` for updates throughout the framework, for
better RESTful semantics. Generic update commands only change the fields present in the body (I-06), which is a
partial update (`PATCH`), not a full replacement (`PUT`).

**Implementation (2026-10-27):**

- Generic entity router: `PATCH /<entity>/{id}` instead of `PUT` (`KiwiRouterFunctionConfig`); the `PUT` route is
  removed without a fallback.
- OpenAPI: the update operation is documented as `PATCH` (`KiwiOpenApiAutoConfiguration`).
- KDocs (`GenericUpdate`, `GenericAnnotations`), comment in `KiwiOpenApiHelper`, `GenericEntityControllerTest`
  (`mvc.patch`).
- Demo: `TodoItemController.moveItemToList` uses `@PatchMapping`.
- Docs: chapters 3, 5, 6 (endpoint tables, partial-update note), 7.
- Kept: `PUT` in the default CORS `allowed-methods` (`KiwiFrameworkProperties`), so applications' own `PUT`
  endpoints keep working.
